# aeb's regen pass should auto-expand transitive project-local imports

**Filed by**: aether toolchain (sibling claude session)
**Date**: 2026-05-20
**Severity**: high — every multi-module aeb project hits this as soon
as a consumer's `.build.ae` forgets to enumerate a transitive
dependency. Currently the failure mode is a gcc link error with no
breadcrumb back to "you missed a `regen_with(...)` line."
**Cross-ref**: misfiled in the aether repo as
`self-directory-import-link-regression.md` (avn port, 2026-05-20). That
report claims an aetherc regression between 0.172 and 0.173; the
investigation below shows the actual gap is in aeb.

## Symptom

`aeb <target>` runs aetherc cleanly (type-check passes) and then gcc
fails with `undefined reference to <symbol>` for every symbol that the
consumer's transitive module graph needs but the consumer's
`.build.ae` doesn't explicitly enumerate.

Concrete reproducer in `~/scm/AetherThings/avn`:

```bash
cd ~/scm/AetherThings/avn
aeb client
# /usr/bin/ld: module_generated.c:(.text+...): undefined reference to
#     `int_vec_new' / `int_vec_count' / `int_vec_get' / `int_vec_add'
#     / `int_vec_free' / `repos_rev_field' / `repos_head_rev'
#     / `repo_primary_hash' / ...
# collect2: error: ld returned 1 exit status
# client: gcc link failed
```

`aeb avn` (sibling target — same `client/module.ae` transitive graph)
builds and links cleanly.

## Diagnosis

`client/test_client.ae` does `import client`. `client/module.ae`
imports `repo_storage`, `util`, `working_copy`, `repos` (project-local
sibling modules). The gcc command line aeb constructs has:

```
gcc test_client.c
    client/module_generated.c
    repo_storage/module_generated.c
    ffi/openssl/module_generated.c
    -laether ...
```

Three `module_generated.c` files. Missing: `util`, `working_copy`,
`repos`. Each of those has a `module_generated.c` already on disk
(generated by aetherc), with the symbol bodies the link is asking for
— they're just not in the gcc invocation.

Why? `client/.build.ae` enumerates the regen list explicitly:

```aether
regen_with("../client/module.ae", "fs,os,net")
regen_with("../repo_storage/module.ae", "fs,os")
regen("../ffi/openssl/module.ae")
```

`avn/.build.ae` enumerates the full transitive set:

```aether
regen_with("../client/module.ae", "fs,os,net")
regen_with("../util/module.ae", "fs")
regen_with("../working_copy/module.ae", "fs,os,net")
regen_with("../repo_storage/module.ae", "fs,os")
regen_with("../repos/module.ae", "fs,net,os")
regen("../ffi/openssl/module.ae")
```

`_run_regen_pass` (`lib/aether/module.ae:909`) iterates the explicit
regen list and appends each entry's paired `_generated.c` to
`extra_source`. The link step links exactly those `extra_source` files.
No transitive expansion — the porter is on the hook for enumerating
every transitive sibling module by hand.

## Why this looks like an aetherc regression from the outside

`client/module_generated.c` (the file aetherc emits for the
`client` module) does include forward declarations of the transitive
symbols — `void* int_vec_new(int);` etc. — but not the bodies. That
gives the consumer a clean type-check (every call resolves to a
declared symbol) and pushes the failure to link time, where the
diagnostic is "undefined reference" with no breadcrumb to "you forgot
`regen_with("../util/module.ae", ...)` in `.build.ae`."

The reporter (avn-port Claude session) saw "type-check passes, link
fails" and reasonably concluded aetherc must have changed how it
emits transitive bodies between 0.172 and 0.173. It didn't — `git
diff v0.172.0 v0.173.0 -- compiler/aether_module.c` is empty.
Whatever shape worked at 0.172 was almost certainly the same
"forward-decl only, link picks up the body from siblings via the
ambient build graph" — and the build graph used to include the
sibling modules through some path that no longer fires.

I haven't traced *why* the build graph was wider at 0.172 (could be
an aeb change, could be that the project's `.build.ae` files used to
list every transitive module and were trimmed during a cleanup
round). Either way, the durable fix is "aeb expands transitively"
rather than "every porter enumerates every transitive."

## Proposed fix

In `_run_regen_pass` (or a preprocessing pass before it),
fixed-point-walk the regen entries the same way
`tools/resolve-imports.sh` already walks SDK imports:

1. Seed worklist with every explicit `regen` / `regen_with` entry.
2. For each `<ae_path>` in the worklist, parse its top-level
   `import <X>` lines (same `sed -n 's/^import \([A-Za-z_][A-Za-z0-9_.]*\).*$/\1/p'`
   that `resolve-imports.sh` uses, or a structural walk via aetherc
   if you prefer not to lean on regex).
3. For each import `<X>` that is **not** `std.*` and **not**
   `contrib.*`: try to locate `<X>/module.ae` in the project tree
   (sibling-of-source-dir, then walking up). If found and not
   already in the regen list, append it. Inherit the caps from the
   parent entry (a transitive sibling needs at least the caps the
   parent declared) or auto-detect from its own imports.
4. Repeat until no new entries were added.
5. Hand the expanded list to the existing `_run_regen_pass` body.

The walk should bottom out at:
- `std.*` / `contrib.*` (resolved at link via `-laether` etc.)
- Modules outside the project root (e.g. system packages)
- Already-seen entries (cycle break — handle the same way
  `resolve-imports.sh` does via the `tmp_seen` / `tmp_prev` cmp-loop)

`resolve-imports.sh` is the right model — POSIX shell, BFS, dedup
via `sort -u`. The regen-expansion pass should look almost identical
except that it filters to project-local imports and emits
`(path, caps)` tuples into the regen list instead of `import X`
lines into a source preamble.

## Workaround until this lands

Project-side: enumerate every transitive sibling module in the
consumer's `.build.ae`. I'm filing a companion note to avn
(`client-build-missing-regen-entries.md`) pointing this out for the
current break.

## Why this is high-severity in the long run

Every multi-module aeb project will hit this the first time a porter
adds a test driver inside a module that imports a sibling. The
failure mode (gcc link error with no aeb-level diagnostic) is
indistinguishable from a real compiler bug — the avn-port report
spent significant time bisecting aetherc before the diagnosis landed
on aeb. A single transitive-expansion pass in `_run_regen_pass`
removes the entire class.

## Optional follow-up: aeb diagnostic when a `module_generated.c`
exists but isn't in the regen list

Even without the transitive-expansion fix, aeb could check: if the
gcc link errors out, scan `<project>/**/module_generated.c` for the
undefined symbol; if a sibling defines it, print
`hint: add regen_with("../<sibling>/module.ae", "<caps>") to .build.ae`.
A single-shot diagnostic that catches the manual-enumeration variant
of the same bug.

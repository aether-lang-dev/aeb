# Versioned BOM + generated self-validating lock (cross-SDK)

**Filed by**: design conversation (Paul + LLM session), generalizing from
the Python SDK's `pip()`/`requirements_file()` model and the Java SDK's
existing `.bom.ae` (`maven.load_bom_file`).
**Status**: design agreed; not yet implemented.
**Scope**: a generic aeb mechanism, with Python / Ruby / Java as the first
consumers. The grammar and node topology are identical across languages;
the only per-SDK divergence is whether the runtime version is an input to
dependency resolution (see § Fidelity asymmetry — do not erase it).

## Motivation

Two problems, one design:

1. **Repetitive needed-version statements.** A `python("3.12")` /
   `jdk("25.1")` / Ruby-version declaration repeated per builder within a
   file, and again across every module in a fleet ("we're a 3.12 shop"),
   restated N times. Implicit inheritance (file-level or root-level
   cascade) would fix it but is *un-aeb*: it's invisible to `grep` and
   requires walking up the tree to know what a module gets. aeb's identity
   is "edges are explicit data, not inherited cascade" (LLM.md: no reverse
   edges, no implicit fan-out).

2. **No lockfile for reproducibility.** `pip("numpy~2.1")` resolves the
   transitive closure at install time but writes nothing back. There is no
   pinned, hash-bearing record of the resolved graph (LLM.md scores
   "Lockfiles for reproducibility" ✗ TODO across all SDKs). A bare
   `requirements.txt` is *less* faithful than aeb could be, because it
   ignores the interpreter axis (see below).

## The design — three node types + a generic self-check

A **two-node split (BOM intent + generated lock result) with a producer
step between them**, plus self-validation that lets a consumer depend on
*only* the lock.

### 1. Versions BOM (hand-authored intent)

Declares the runtime version + dep version pins. Per language:
`pip_versions.ae`, `gem_versions.ae`; for Java this **already exists** as a
`.bom.ae` consumed by `maven.load_bom_file` — do NOT invent a second Java
form, generalize the existing one.

The "level" at which versions apply is **the file's location + who deps
it**, NOT a cascade:
- root-level `pip_versions.ae` dep'd by 40 modules → fleet-wide.
- a `services/pip_versions.ae` dep'd by 6 modules → a sub-fleet.
- a second BOM for the one module on 3.13 → divergence, *explicit*, no
  override-magic. `grep -rl pip_versions.ae **/.build.ae` answers "who is
  on this set" — same answer-shape as every other aeb dependency question.

This subsumes both "file-level" and "root-level" repetition fixes: the
location IS the level.

### 2. Lock generator (hand-authored build target)

A target run as `aeb .<lang>_make_lockfile.ae`. It `dep()`s the versions
BOM, resolves the transitive closure **for the BOM's declared runtime**,
installs, and **emits the generated lock node** (§3). Being downstream of
the BOM via a real `dep()` edge is load-bearing: the generator must read
the BOM to know the interpreter, or it resolves against PATH's `python3`
and emits a cp-mismatched lock.

### 3. Generated self-validating lock (machine-authored result)

Generated `.ae`, committed, greppable, dep-able — but **never
hand-edited** (a build step writes it; that is what reconciles "lock is
`.ae` grammar" with "humans must not hand-maintain a transitive closure").
It carries, as generated data:

```
// GENERATED by `aeb .pip_installs_and_make_lockfile.ae` — do not hand-edit
generated_from("pip_versions.ae", "sha256:a1b2c3…")  // hash of the BOM it came from
locked_for("cp312")                                  // runtime tag (see fidelity note)
locked("numpy==2.1.0",  "sha256:…")
locked("pytest==8.2.1", "sha256:…")
// … full transitive closure …
```

**Self-validation, on every visit of the lock node** (implemented once in
`lib/build`, called by each SDK's lock builder — `_validate_generated_lock`
— so the check can't drift into three copies, cf. the `file_to_label`
three-copy lesson):

- Re-read the file named in `generated_from`, hash it, **hard-fail if it
  ≠ the embedded sha256** ("lockfile stale vs pip_versions.ae — re-run
  `aeb .pip_installs_and_make_lockfile.ae`").
- **Hard-fail if that file is missing** ("lock references pip_versions.ae
  which is gone") — do not silently pass.
- **Hard-fail if the selected runtime ≠ `locked_for`** — guards the
  consumer-side override case (a `python("3.13")` on the consuming builder
  diverging from a 3.12 BOM). The `generated_from` hash already catches
  BOM drift; `locked_for` catches consumer override. Two drift vectors,
  two guards.

### Why a content hash, not a `dep()` edge, to the BOM

The lock expresses "I derive from the BOM" as an **embedded content hash**,
NOT as a `dep()` edge to `pip_versions.ae`. This is a deliberate, slightly
unusual choice: an edge would force every consumer of the lock to also pull
the BOM into its graph; the hash does not. The payoff is the key ergonomic:

```
python.test(b) {
    dep("./pip_lockfile.ae")   // ← ONLY the lock. It self-certifies.
    pip("pytest~8.2") ...
}
```

The consumer deps the lock alone. Validation is the lock node's own job,
fired unconditionally on every visit, for every consumer — so there is no
"consumer forgot to dep the BOM → skipped the check" failure-skip path.
The hash pins the *bytes* of the BOM, a stronger assertion than an edge
(which only pins the relationship).

### Edge order does not matter (and must not)

`build.dep()` is a runtime no-op; the DAG is built from textual extraction
and topo-sorted before any `.ae` runs. The order of two `dep()` lines in a
consumer is obliterated by topo-sort. The consistency guarantee comes from
the embedded hash checked at the lock node, never from source-line order.
Do not design anything to rely on line order.

## Fidelity asymmetry — do NOT erase it

"As similar as possible across Java / Ruby / Python" means **identical
grammar and node topology**, with **per-SDK semantics for whether the
runtime version is a resolution input**. Forcing the internals symmetric
would be a fidelity bug:

| | Python / Ruby | Java |
|---|---|---|
| Runtime version in dep identity? | **Yes** — `cp312` wheel tag / Ruby native-ext ABI | **No** — `junit:5.10` is one jar across JDK 21/25 |
| Runtime ↔ resolution | **Entangled** (version is a resolver input) | **Orthogonal** (toolchain axis separate from classpath) |
| Lock validity | **Per-runtime-version**; bump → re-resolve → different closure | **Pan-version**; resolved classpath unchanged across JDKs |
| `locked_for(tag)` | **Load-bearing gate** | Recorded but informational |

So: Python/Ruby SDKs feed the selected runtime into resolution and treat
`locked_for` as a hard gate. Java records `locked_for` (e.g. "resolved
under maven X") but it does not gate on JDK version, because the classpath
is JDK-independent. A future session must not "fix" Java to be per-JDK to
match Python — that would claim a cross-version cache hit that is a lie for
Python and meaningless for Java.

Today's latent hole this also closes: `lib/python/_ensure_venv` hardcodes
`python3 -m venv` (PATH's interpreter), and nothing records which version
built the venv — so Python builds are silently bound to an undeclared
runtime. The BOM's `python("X.Y")` must drive a version-tagged venv
(`.aeb/venv-py312`) and fold the interpreter into the wheel-resolution
cache key.

## Generic mechanism, SDKs as consumers

The reusable core lives in `lib/build` so every SDK shares one
implementation and they cannot drift:
- `_validate_generated_lock(ctx)` — the hash / missing-BOM / `locked_for`
  checks.
- the `generated_from` / `locked_for` / `locked` setter grammar (or a
  shared helper each SDK's lock builder calls).

Each language SDK provides: a `<lang>.make_lockfile` builder (the generator
target's entry point) and a consumer-side path that installs the locked
closure. The consumer grammar is identical across languages (dep the lock,
the lock self-validates).

## Acceptance

- A module's `.build.ae` deps **only** `<lang>_lockfile.ae` at test/build
  time; the lock self-validates against the BOM hash it embeds.
- Changing the BOM without regenerating the lock → **hard-fail** naming the
  regenerate command, on the next build that visits the lock.
- A deleted BOM, or a consumer-side runtime override diverging from
  `locked_for` → hard-fail.
- `aeb .<lang>_make_lockfile.ae` (re)generates the lock with a fresh
  `generated_from` hash + `locked_for` tag + the resolved closure.
- Python/Ruby: bumping the BOM's runtime version re-resolves to a different
  closure and the version is in the resolution cache key. Java: the same
  grammar works, `locked_for` is informational, classpath is JDK-independent.
- The version-set is declared once per BOM file; modules dep it (directly
  or transitively via the lock) — no per-builder or per-module repetition.

## What is NOT being asked

- NOT a toolchain *provisioner*. `python("3.12")` / `jdk("25.1")` select
  among **already-installed** runtimes (discover-select-or-fail), and fail
  loudly naming what was found if none match. Installing a runtime stays
  the user's / CI's job (sdkman, apt, `actions/setup-java`). aeb is a
  build engine, not a toolchain manager (LLM.md Nix §).
- NOT an external-lockfile parser. aeb does not parse `requirements.txt` /
  `Gemfile.lock` / a foreign lock format. `requirements_file(...)` /
  `Gemfile` remain the *import* path for repos that already have one; the
  generated `<lang>_lockfile.ae` is aeb's own artifact.
- NOT inheritance/cascade for versions. Scope is the explicit `dep()` edge
  + file location, never a walk-up-the-tree rule.
